How it works.

01 / 16

Turns on its own  ·  ← → to move  ·  Enter to open  ·  Esc to close

A support chatbot that remembers you on the web, on Telegram and on Discord — because all three read and write the same memory on Walrus mainnet.

Built for Walrus Sessions 8: Chatbots That Remember (Sept 18 – Oct 9, 2026). Runs on open-weight models via OpenRouter (Kimi K2.5, DeepSeek v3.2 fallback) — no Claude, no GPT.

Most "chatbot with memory" demos remember you within one app. Move to another device or another platform and you are a stranger again, because the memory was never really yours — it was a row in that app's database.

Here, memory is a set of blobs on Walrus, keyed to a person rather than to a surface. Type /link on Discord, redeem the code on Telegram, and the two accounts collapse into one person who is remembered in both places. Nothing is copied between them; the namespaces are simply read together.

They used to keep a copy each, which is how /mode came to be registered with neither of them while working perfectly if you typed it. tools/check-bots.mjs now fails if Discord stops offering something the shared menu lists.

Buttons, not memorised commands

A bot whose abilities are invisible until you read its help is a blank box that happens to accept slashes. So a reply that has an obvious next step carries it as a button: What do you know about me? after /help, Connect another app after a link code, See everything I remember — a link straight to the memory page — after a list of facts.

The actions are named once in src/core/commands.mjs and drawn by each surface in its own idiom: Telegram makes an inline keyboard, Discord a row of components, and either can carry a link button. A command added to that registry becomes a button on both bots without either adapter changing, which is what stops the three surfaces drifting apart.

A tapped button runs the command it stands for through exactly the same path as typing it: same memory, same writes, same streaming. The button is a shortcut for the person, never a shortcut in the code — and /forgetme keeps its two-step confirmation on both bots, because a destructive thing one tap away is a destructive thing done by accident.

Laid out, not printed

Conversation stays as streaming text: a chat should look like a chat. A command's answer is not conversation — it is a list, or a code — so the structured half of what handleCommand returns travels as data and each surface lays it out its own way. Discord gets an embed with the brand colour and every memory linked to the blob that holds it; Telegram gets the same in HTML, with link previews off so ten memories don't drag a preview card behind them.

HTML rather than Markdown on Telegram, and only for these: a memory is whatever somebody typed, and one unbalanced * in it makes Telegram reject the whole message rather than render it plainly. That is how a memory list becomes silence. In HTML three characters need escaping and they always can be.

The bots' own profile

Telegram gets a description (the text on the empty chat, its one chance to explain itself before being spoken to), a short description for its profile card, and command lists scoped per chat type — a group is never offered /whatyouknow, because printing someone's memories into a room full of people is not a thing to put one tap away. Discord sets its own avatar on first connect and a listening status.

The mark itself is src/web/assets/avatar.png: the site's own icon, rendered and re-centred so it survives a circular crop down to 32px.

  • Writing. Conversation turns go to the relayer's analyze(), which extracts discrete facts server-side inside the TEE. The raw conversation is never sent to the chat model just to be summarised, and fact extraction costs no model tokens. Turns carry an occurredAt anchor so "next Friday" is resolved to a real date before it is embedded.
  • Reading. Recall runs across every namespace the person owns (their own, plus any merged in by linking), budgeted with maxTokens so a long memory never crowds the context window, and weighted slightly toward recency so a correction beats the thing it corrected.
  • Receipts. A memory exists only when a confirmed blob_id comes back. Every confirmed write is appended to blob-ledger.jsonl and served at /api/ledger, so any blob id can be checked on Walruscan. The web chat shows them landing live.
  • Identity is exact, never semantic. A surface account maps to a person via a namespace derived deterministically from its id. Identity is never resolved by vector similarity — a "close enough" match would hand one user another user's memories.
  • Recalled text is data, never instructions. Memories are fenced in the prompt and the model is told they can be written by anyone. In a multi-user bot this matters: a memory one person creates can surface in another's context.
  • Supersession. Walrus Memory is append-only, so mutable records (identity, opt-out) are superseded rather than edited, and the current value is selected on created_at — not on relevance rank, which happily returns stale records. See docs/memwal-feedback.md.

/chat, /memory and /history are three panels in one document, not three pages. Switching between them shows one and hides another — the header is never replaced, no script re-runs, and a panel you have already opened keeps its scroll position, its data, and whatever you had typed. A lap around all three reads nothing from Walrus; measured, a switch takes about 30ms.

The header carries two pills, Chat and Memory. Past conversations live in the rail beside the chat, listed with which app each one happened on — seeing "Telegram · 2h ago" in the web sidebar is the cross-surface story without a word of explanation. The History panel is still there behind "See all", with search across everything and the Walrus blob badges; it just no longer needs a pill.

They stay three separate source files, because they collide everywhere: .list and .sub mean different things in each, and --r is 24px in chat and 20px in the other two. npm run build scopes each panel's CSS under its own id and re-points its variables, then writes src/web/app.html.

Edit chat.html, memory.html or history.html, then run npm run build. Never edit app.html — it is overwritten. Each source page is still served at its own .html name, so either half can be opened standalone when something breaks and you need to know which one owns the bug.

/memory is a shelf of collections rather than one long list: Photos, Still open, Plans, Your setup, Projects & work, Preferences, About you, and Everything else. A memory lands on the first shelf whose keyword test matches, in that order, so "stuck on a 403" is Still open before it is anything else and an interview on Thursday is a plan before it is the tools it names. Keyword tests, not a model: they run on every render, and being wrong costs a memory sitting one shelf over.

Covers are drawn in type: an ASCII figure for each shelf over a field of scattered characters seeded from the shelf's name, so every cover differs and every reload draws the same one. Photos shows a collage of real pictures instead, once there are any.

Each cover opens into its collection, where every memory still carries its date, the app it was written on, whether it was ever read again, the id of the blob that holds it, and "Not right". Photos are a grid with a lightbox, built from the picture namespace (listImages()), with the vision model's description and what you said when you sent it. Which collection is open lives in the URL hash, so the back button steps out of it.

While it thinks

The three dots are gone. A turn opens with a slate in the reply bubble: Reading your memory with a clock, then Thinking, then Saving to Walrus (which happens after the reply, through the outbox). The server sends one stage event on the stream when recall finishes — how many things it found, how many pictures, how long that took — and the first streamed word replaces the slate. Past six seconds the label changes to "Memory is slow right now", because a slow relayer read looks exactly like a hung page without a clock on it.

Above the composer sit quick controls: New chat (also ⌘K / Ctrl+K), What do you know about me?, Bring back a picture (prefills the composer), Summarise this chat, and Link Telegram or Discord. New chat was in the ⋯ menu before, and nobody found it.

A chatbot that remembers has nothing to show in its first conversation, so a new person can choose to be introduced first. /welcome asks five things, one to a screen, every one skippable: a name, what they want it for, how they like answers (plus their tools, if they picked coding), a picture, and their other apps. Someone arriving at the site for the first time is sent there by the landing page's own button; anyone this browser has seen before goes straight to the chat, and the introduction is one tap to leave from every screen. It is also offered from a card on the chat's empty state, and never stands in the way of just talking.

Every answer is an ordinary memory (src/core/onboard.mjs): written verbatim to the person's own namespace through the outbox, one blob per step rather than per chip, with its blob id shown on the page as it lands. Nothing is kept in a side table, so a wrong answer is corrected on the memory page like any other. The picture goes to the picture bank. A record in ws8::onboard::<person> marks it done, so opening it again starts from the earlier answers and writes only what changed.

Afterwards the chat greets them by name and offers starters that match the jobs they chose, and the first real message is answered using the name, the tools and the preferred length and tone.

Four of them — Tutor, Coding partner, Planner, Support desk — and none by default. A mode changes the manner and nothing else: the same memories, the same namespace, the same person answering. One that also partitioned memory would turn a single assistant that knows you into four that each know a quarter, which is the thing this was built to avoid.

It is stored in ws8::mode::<person>, superseded on change and cached per person, which makes it a memory rather than a session setting — so choosing Tutor on Telegram is choosing it on Discord and the web. That is the cross-app claim demonstrated in one tap rather than described.

/mode on either bot lists them as buttons; the web has the same thing as chips. The introduction already asks what you want it for, and four of those six answers are modes, so picking "a tutor" there sets it rather than asking the same question twice.

It offers, once

A message that plainly asks to be taught, or carries a stack trace, gets a sentence at the end of the reply asking whether you want that mode — with a button next to it. Only ever to someone who has not chosen: once you have picked, being nudged elsewhere is second-guessing you, and this exists for people who do not know the feature is there. At most one offer every twenty minutes, so a decline is respected.

The overlays are about manner and grant nothing. tools/check-bots.mjs asserts that, along with every mode having a button on both bots.

An image cannot itself be a memory: Walrus Memory stores text, and every write method on the SDK takes a string. What can be a memory is a description — and a good one outlives the file. "A 403 from publisher.walrus.space with an empty Authorization header" is worth carrying to Telegram; the PNG is not.

So an attachment takes two paths. A small vision model reads the image and the description goes into memory like anything else said in that conversation, which means it crosses surfaces and shows up in recall. The bytes are kept and served back separately.

The looking is done by a cascade, not one model: qwen/qwen3.8-flash, then qwen/qwen3-vl-8b-instruct, then meta-llama/llama-4-scout (override with VISION_MODEL, comma-separated), in three rounds. One evening the first was rate-limited upstream for an hour and every photo sent in that hour came back "could not read", which meant unfindable for good. The browser also shrinks photos over 600KB to 1600px before upload; a 2MB phone screenshot was pushing the model past its 40-second limit for no gain in what it could see.

Text files

A .txt, .md, .csv or .json is read rather than looked at, and the words become the memory. A short one is kept verbatim — nothing a model could write about a two-line note is more findable than the note. A longer one gets a description in the same spirit as a photo's, with the exact names, errors and numbers preserved and its opening quoted, then flows into memory by the same path an attachment always has.

Send a deployment runbook and ask a week later where the volume is mounted; the answer comes from the seven facts the file turned into, each its own blob.

PDFs are no longer offered. The accept list used to include them and stored "a PDF file named report.pdf (240KB)" — a sentence matching nothing anyone would ever search for, so the file was lost the moment it arrived. Extracting text from a PDF needs a real parser, and half-accepting one is worse than saying no; they belong to the v2 plan, where a file becomes a blob in its own right. tools/check-files.mjs fails if the accept list ever offers something documents.mjs cannot read.

Worth being precise about what is durable: the description is on Walrus, the file is on disk. On a platform with an ephemeral filesystem the file does not survive a redeploy and the memory of it does. Putting the bytes on Walrus too needs either a publisher (there are no public unauthenticated publishers on Mainnet) or rememberManual(), which accepts SEAL-encrypted bytes and an embedding you generate yourself — a second implementation of the memory layer rather than a flag to flip.

When memory does not answer

The relayer returns nothing for a matching query about four times in ten, and rate-limits on top. Three rules keep that from showing:

  • What it read last is still true. The agent keeps each person's last non-empty recall for six hours and falls back on it when a turn's recall comes back empty or fails, marked to the model as not a fresh search.
  • Known is not the same as readable. If a person's namespace has ever held anything, the model is told it knows them even when nothing could be read, and it is forbidden from calling this a first conversation or saying it has no memory of them. tools/check-known.mjs produces that failure on purpose and reads the replies for the sentences it must never say.
  • A write is never dropped for want of a read. When the opt-out cannot be read, the write is queued with a guard and the outbox asks again before it sends. Pictures still in the queue are found by findImages() too, so "did you keep that photo?" a minute after sending it is answered yes, with the photo.

Transcripts live in their own namespace, apart from memories, because the two want different handling: a memory is a fact worth keeping forever and gets extracted, deduped and recalled semantically, while a transcript is read whole and in order.

One blob per conversation, not per turn — writing every message would double the cost of a turn against an hourly quota that is already tight. A conversation saves itself once it goes quiet, and on SIGTERM, so a redeploy does not eat what is in flight. The save goes through the same outbox as every other write: for a while it was a direct call, and a conversation that closed during a relayer rate limit was logged and lost.

Relative dates are pinned to the calendar in the text that gets stored: "interview on Thursday" is written as "interview on Thursday (1 Oct 2026)" (time.mjs, deterministic, no model). The model is told today's date and what the brackets mean, so it can tell what has happened from what is still to come.

Once a plan's day has passed, the bot asks about it — once. Each turn looks at the dated memories already in context (plus one extra read for dated plans on a person's first message of the day) for a plan whose date fell in the last ten days, hands the model a single follow-up note, and records it as asked in followups.json beside the outbox (followups.mjs). Asking about the same interview every message would be worse than never asking.

Recall is conversation-aware: a short or anaphoric message ("and the second option?", "yes, that one") is searched with the previous user turn in front of it, and extraction is given the assistant's question a short answer replies to, so "yes, part-time" becomes a fact about the person instead of nothing. Same number of reads either way.

The direction this is heading, after the hackathon submission: an AI workspace rather than a chat window, where conversations, memories, files and things the assistant makes for you all hang off the same identity.

  • Files as first-class memories. The rememberManual() path — SEAL encryption and embeddings generated client-side — so a PDF or an image is itself a blob the account owns, not just a description of one.
  • Things the assistant creates. Ask for a to-do list and get a real page, saved under What I Created, openable and editable later. This needs the model to call tools rather than only answer, plus somewhere durable for the artefacts and a way to version them.
  • Spaces. Sections a person or the assistant can create to group related conversations, files and artefacts.

The hard part is not the UI. It is that an artefact is mutable and Walrus is append-only, so editing a page means superseding it — the same problem identity records already have, at a larger size and with a version history people expect to be able to walk back through.

What building on Walrus Memory turned up, with reproductions. Filed as the bug-bounty part of the submission.

MemWal feedback from building this bot

Found while building a multi-surface chatbot on @mysten-incubation/memwal@0.1.7 against the mainnet relayer (relayer.memory.walrus.xyz, apiVersion 1.0.0, relayerVersion 0.1.0).

Bug 1 — recall intermittently returns an empty result set

Severity: high. This is the one that matters. For a memory product it is close to existential, and it hides itself completely.

The same recall() call, against the same namespace, with the same query, sometimes returns total: 0, results: [] — and sometimes returns the matches. Nothing distinguishes the two responses. There is no error, no flag, no dropped_count.

Reproduction

Namespace ws8::person::199d6d8a-… holds 13 memories. Fourteen identical calls, 800 ms apart:

for (let i = 0; i < 14; i++) {
  const r = await memwal.recall({ query: "publisher 403", namespace: NS, limit: 5 });
  process.stdout.write(r.results.length + " ");
}
// 5 5 5 5 0 0 5 5 0 0 0 0 5 5      → empty on 6 of 14

Runs are not independent — the zeros arrive in clusters, which suggests a window of bad state (a replica, a cache, an index lease) rather than a per-query dice roll.

Why it matters

An empty recall is indistinguishable from a namespace that genuinely has nothing in it. That is the expected response for a first-time user, so no caller can detect the failure: a memory-backed chatbot simply greets a returning user as a stranger, at random, roughly 40% of the time. Nothing logs an error. The bug is invisible from the outside and destroys the product's only promise.

This compounds with the absence of a no-match signal (previously raised as MemWal #741): callers cannot tell "nothing stored" from "lookup failed", so there is no way to build a correct client on top of the current contract.

What it actually cost us

Not a degraded answer — a user's entire history.

Identity here is a record in a key-like namespace (ws8::id::web::<account>). On a cold start the bot reads it to learn who you are. One of those reads came back empty five times running, so the bot concluded it had never met this account and minted a second person for it. Because append-only storage means "current value" is the newest record, every later read returned the new, empty person, and the four memories under the original were orphaned permanently:

ws8::id::web::web-proof-2 →
  d083f353-…   (minted by the false empty — no memories)
  fcc93702-…   (the real one — 4 memories, now unreachable)

Nothing errored. The user would simply have been greeted as a stranger forever.

We now defend against this in two ways: identity reads retry far harder than ordinary recalls (an empty answer there is indistinguishable from "new user", and acting on a false one is unrecoverable), and duplicate identity records are healed rather than resolved newest-wins — every person id ever recorded for an account is folded into the namespace union, so a split account knits itself back together. Both are workarounds for the flake, not fixes.

Suggested fix

Fix the flake, but also make it detectable: distinguish "no matches" from "search did not run" in the response. Even a boolean would let callers retry honestly instead of silently serving amnesia.

Workaround in this codebase

recall() in src/core/memory.mjs retries on empty — four attempts with exponential backoff (200/400/800/1600 ms). That took the observed empty rate from 6/14 to 0/16. Retrying on empty is only acceptable because a genuinely empty namespace is cheap to re-query; it should not be the application's job.

Bug 2 — rememberAndWait reports failure on writes that succeed

Severity: medium-high. Causes duplicate memories and double spend.

rememberAndWait(text, namespace) polls with a 60 000 ms default and throws 504 remember job timed out. On mainnet, jobs routinely exceed 60 s and then complete normally.

await memwal.rememberAndWait("the project codename is Halibut.", "ws8::test::smoke");
// throws: Error: remember job timed out after 60000ms (job_id=7b213135-…)

await memwal.getRememberStatus("7b213135-f4ff-4dd4-862e-4fa084607ce3");
// { status: "done", blob_id: "1orLRyP-9HQB95NSyxHmC92QdZnpUW6rbI1MGgRTDic", … }

Observed round trips ranged from ~34 s to well over 90 s for a single small fact.

A caller that reads the throw as failure and retries writes the same fact twice. Both are real blobs, both are paid for, and both return on every later recall — we saw a retried fact come back as two hits at distance 0.450 and 0.458, with nothing marking one as a duplicate.

Suggested fix: raise the default past the observed p99; or throw a distinct pending error so "not yet" is not shaped like "failed"; or apply idempotencyKey automatically inside rememberAndWait.

Workaround: rememberFact() waits 180 s and, on timeout, returns { pending: true, jobId } for later settlement via getRememberStatus — it never re-sends the text.

Bug 3 — a reused idempotency key is a permanent lockout

Severity: medium. Correct server behaviour, but the failure is terminal and undocumented.

Writing with an idempotencyKey that was already used with different content returns:

409 {"error":"idempotency_key was already used for a request with different content"}

That is reasonable in isolation. What makes it a trap is that it never expires. A caller using a natural stable key (user:<id>) whose payload contains anything volatile — a createdAt, a display name, a counter — poisons that key permanently on the first retry. Every subsequent write under it fails forever. We locked out a live Telegram account this way and the only symptom was silence.

Suggested fix: document the constraint prominently, and consider scoping the key's uniqueness to a TTL so a stale key eventually frees.

Workaround: bind the key to a hash of its own content (${key}:${sha256(text).slice(0,12)}), which makes key and payload consistent by construction — identical writes dedupe, changed writes get a fresh key.

Reliability — transient 5xx on analyze

Intermittent 500 Internal server error from analyzeAndWait under normal load (e.g. traceId ec68f0fd-4443-4bda-a147-3f938f61eabb), alongside occasional Upstream Unavailable: Memory encryption backend is unavailable and bare fetch failed. All cleared on retry within seconds; health() reported status: ok, write_ready: true throughout, including while writes were failing.

Two asks: have health() reflect degraded write capability, and note in the docs that analyze/remember need client-side retry. A write path that silently drops a memory on a hiccup is a bad default for a memory product — the reply has already been sent to the user, so nothing surfaces the loss.

Bug 4 — bulk writes report failure as a value nobody checks

Severity: medium. Silent data loss, same family as the two above.

rememberBulkAndWait() resolves when individual items fail — the failures are entries inside results, not an exception. Any caller with retry logic wrapped around the call never sees them, and a caller that counts successes loses the rest without a word.

Seeding a knowledge base, 190 statements went in and 113 landed. Nothing threw. The 77 that vanished only became visible after we started inspecting every result entry, and the cause was transient and eminently retryable:

failed: Upstream Unavailable: Memory encryption backend is unavailable
timeout: polling timed out after 300000ms

Both cleared on a retry seconds later.

Suggested fix: either reject when every item in a batch fails, or document prominently that per-item status must be inspected. The current shape means the happy path and the 40%-data-loss path look identical to a caller.

Workaround: rememberMany() in src/core/memory.mjs inspects every entry and retries the failures itself with backoff, because the outer retry wrapper cannot see a failure that arrives as a value.

Operational — the rate limits are easy to hit and undocumented in the SDK

There are at least two layers, and only one of them is obvious:

layerlimitretry_after_seconds
account_sustained1000 weighted-requests/hour300
delegate_key60 weighted-requests/min60

The per-minute one caught us out late. An hourly ceiling you can pace against; a 60/min burst limit is something a normal chat turn can trip on its own, because one turn spends several requests. Running an end-to-end test suite of twenty-odd HTTP calls hit it immediately, and the error surfaces at the SDK boundary as a generic 500 wrapping the real message:

remember job failed: Internal Error: seal encrypt failed:
seal/encrypt failed during read_account_identity: RpcError: Too Many Requests

That is a 429 reported as a 500, with the actual cause buried three layers down. Nothing in it is machine-readable, so a caller cannot back off correctly — err.status says 500, and honouring retry_after_seconds is impossible because the field is not there.

Seeding a few hundred knowledge-base facts and capturing a dozen conversations reached it inside an hour, and the symptoms before the 429 finally surfaced were indirect: writes that never landed, recalls that returned empty, jobs that timed out. All of which look like the flakiness described above, so the limit is easy to mistake for instability.

Three asks: surface the weighting (what counts as a weighted request, and what a recall or a bulk write costs); document both layers next to the methods that consume them; and propagate the 429 with its retry_after_seconds intact rather than re-wrapping it as a 500. A caller with no visibility into its own budget cannot pace itself, and one that cannot tell a rate limit from a server error will retry into the wall.

Worth noting for anyone building on this: a chatbot spends several weighted requests per turn — identity read, personal recall, knowledge recall, then the writes — so 1000/hour is a real ceiling, not a theoretical one.

Minor — client sends malformed bodies instead of validating

rememberAndWait is positional (text, namespace). Passing the object form that recall() accepts ({ text, namespace }) is not caught client-side; it is serialised into the request and the server answers:

422 Failed to deserialize the JSON body into the target type:
text: invalid type: map, expected a string at line 1 column 8

TypeScript users are protected; JavaScript users get a deserialiser error that never mentions the argument shape. A typeof text !== "string" guard would fix it. recall() accepting both object and positional forms while remember* does not is what makes this easy to hit.
